# 2024-03-12

Spent the afternoon on the deadlock in the enrolment job. Two workers were updating the same
two course rows in opposite orders: worker A locked course 12 then 40, worker B locked 40
then 12. Postgres detected it after `deadlock_timeout` (1s) and killed one transaction.

Fix: sort the course ids before `SELECT ... FOR UPDATE` so every transaction takes locks in the
same order. Also added a retry on `DeadlockDetected` just in case.

Useful query to see who is waiting on whom:

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

And to reproduce it locally:

```bash
# run two enrolment workers against the same batch
python -m jobs.enrol --batch 7 & python -m jobs.enrol --batch 7
```
